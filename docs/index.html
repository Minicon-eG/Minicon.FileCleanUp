01 / KONZEPT

Ziel und Zuständigkeiten

Minicon.FileCleanUp löscht veraltete Dateien anhand expliziter Regeln und dokumentiert die Entscheidungen. Die Kundenanwendung ist eine eigene Console. Sie bindet das NuGet-Paket ein und wird regelmäßig über die Windows-Aufgabenplanung gestartet. Ein Lauf arbeitet seine Regeln einmal ab und endet.

appsettings + eigener Provider→Kunden-Console→NuGet-Bibliothek→Dateisystem
Bibliothek / ILogger→Logging der Console→Lokaler Puffer + Seq

Kein eigener Dienst, kein eingebauter Webserver und keine Zeitsteuerung im Paket. Die HTML-Seite ist eine statische Hilfe, keine Oberfläche zum Auslösen von Löschungen.

Erstes Supportziel sind kontrollierte Windows-Ablagen, lokal oder über UNC. Eine portable Implementierung ist sinnvoll; Linux-Unterstützung wird erst nach gesonderten Tests zugesagt. .NET 10 ist die vorgeschlagene LTS-Basis; die aktuelle Supportpolitik nennt Unterstützung bis November 2028. Microsoft: .NET-Support.

02 / ANWENDUNG

Erste Verwendung

  1. Die Kunden-Console mit eingebundenem Paket bereitstellen. Einstellungen und Logging richtet der zuständige Entwickler ein.
  2. Einen konkreten Ablageordner und die gewünschte Aufbewahrung festlegen. Aktive Arbeitsdateien über Ausschlüsse schützen.
  3. DryRun: true setzen und die Console mit demselben Konto wie später in der Aufgabenplanung ausführen.
  4. In Seq den Lauf über RunId öffnen. Kandidaten, Stichtage, ausgeschlossene Bereiche und voraussichtlich leere Verzeichnisse prüfen.
  5. Für den produktiven Lauf DryRun: false setzen. Beim ersten Lauf ein überschaubares Löschlimit verwenden.
  6. Abschlussstatus und Fehler prüfen; anschließend den regelmäßigen Start einrichten.
Der Zielordner bleibt immer bestehen. Gelöscht werden geeignete Dateien und – bei eingeschalteter Option – leere Unterverzeichnisse. Die Löschung erfolgt dauerhaft, ohne Papierkorb oder Wiederherstellung im Produkt.

Eine Datei mit altem Änderungsdatum kann fachlich weiterhin benötigt werden. Der Betreiber legt geeignete Ablagen, Fristen und Ausschlüsse fest. Besonders aktive Exportprozesse sollten zunächst in ausgeschlossene temporäre Dateien schreiben und erst nach Abschluss umbenennen.

Beispiel

Bei Laufstart am 2026-09-14T02:00:00Z und 90 Tagen Aufbewahrung lautet der Stichtag 2026-06-16T02:00:00Z. Ein Änderungsdatum davor macht die Datei zum Kandidaten, ein Datum genau auf dem Stichtag nicht. Weitere Bedingungen wie Muster und Ausschlüsse müssen ebenfalls erfüllt sein.

03 / REFERENZ

Konfiguration und eigene Provider

Der Abschnitt heißt standardmäßig FileCleanUp. Die Console übergibt einen IConfigurationSection. Das Paket liest keine Dateien selbst und kennt weder kundenspezifische Provider noch deren Zugangsdaten.

Pfadtrenner in Dateimustern sind ungültig.

Verzeichnisse mit Glob und regulären Ausdrücken auswählen

Directories und ExcludeDirectories unterstützen bereits im vorgesehenen ersten Release die Arten Path, Glob und Regex. Der Typ wird ausdrücklich über Kind angegeben. So werden Punkte, Klammern oder Sternchen nicht versehentlich als andere Mustersprache interpretiert. Beide Listen verwenden einheitlich Objekte; die bisherigen String-Listen werden im Entwurf durch diese Form ersetzt.

{
  "Directories": [
    {
      "Kind": "Glob",
      "Root": "D:\\Kunden",
      "Pattern": "**/Exports"
    },
    {
      "Kind": "Regex",
      "Root": "E:\\Import",
      "Pattern": "Mandant-[0-9]+/Archive"
    }
  ],
  "ExcludeDirectories": [
    {
      "Kind": "Glob",
      "Pattern": "**/Protected"
    },
    {
      "Kind": "Glob",
      "Pattern": "**/Temp/**"
    },
    {
      "Kind": "Regex",
      "Pattern": "(?:.*/)?(?:Backup|Archiv)-[0-9]{4}(?:/.*)?"
    }
  ]
}

Das Beispiel ist ein Ausschnitt einer Regel. Der erste Selektor wählt alle Ordner namens Exports unter D:\Kunden aus, auch direkt darunter. Der zweite wählt beispielsweise E:\Import\Mandant-42\Archive. Protected, Temp und die angegebenen Backup-/Archivordner bleiben mitsamt ihren Inhalten ausgeschlossen.

FeldDirectoriesExcludeDirectories
KindPflicht: Path, Glob oder Regex.Pflicht: Path, Glob oder Regex.
RootPflicht: absoluter, existierender lokaler oder UNC-Verzeichnispfad ohne Muster. Path wählt genau diesen Ordner.Nicht zulässig; Bezug ist immer der Root des zugehörigen Zielselektors.

Ein fester Root ist erforderlich: Ein Regex beschreibt ein Muster, aber keinen Startpunkt für eine Dateisystemsuche. Deshalb wird z. B. Root=D:\Kunden und Pattern=**/Exports verwendet, statt einen beliebigen Ausdruck über alle Laufwerke auszuwerten. Auch UNC-Freigaben sind über einen festen Unterordner als Root möglich. Der Root selbst ist bei Glob/Regex kein Treffer; zur direkten Bereinigung des Roots dient Kind=Path.

Präzise Mustersemantik

  • Pfadtexte für den Vergleich verwenden immer /, ohne führenden oder abschließenden Trenner, z. B. Mandant-42/Exports/Protected. Der physische Root darf Windows-Backslashes verwenden. Bei Path und Glob werden Trenner normalisiert; Regex-Ausdrücke werden nicht umgeschrieben.
  • Glob: * passt auf null oder mehr Zeichen innerhalb eines Pfadsegments; ? auf genau ein Zeichen innerhalb eines Segments. ** ist ein vollständiges Segment und steht für null oder mehr Verzeichnisebenen. **/Protected trifft Protected in jeder Tiefe; Temp/** trifft Temp selbst und seinen Teilbaum. Eingebettetes abc** wird abgelehnt.
  • Glob und Regex müssen den ganzen relativen Pfad treffen. Regex wird intern mit \A(?:Pattern)\z umschlossen. Backup trifft daher nur Backup direkt unter dem Root; (?:.*/)?Backup trifft diesen Namen in beliebiger Tiefe.
  • Windows-Vergleiche sind standardmäßig unabhängig von Groß-/Kleinschreibung. Regex nutzt .NET-Syntax mit IgnoreCase und CultureInvariant; explizite lokale Regex-Optionen können dies innerhalb des Ausdrucks verändern. In JSON muss ein Regex-Backslash doppelt geschrieben werden: "Mandant-\\d+/Archive". [0-9]+ vermeidet dieses Escaping.
  • Mehrere Zielselektoren sind ODER-verknüpft. Jeder Ausschlusstreffer gewinnt. Ein ausgeschlossener Ordner wird nicht betreten, und kein Kind darin kann durch einen anderen Einschluss wieder zugelassen werden.
  • Literalpfade und Globs dürfen weder absolut sein noch ..-Segmente enthalten. Regex wird nur auf bereits innerhalb des Roots enumerierte Pfade angewandt und kann den Suchbereich nicht erweitern.

Zielauswahl und rekursive Bereinigung sind getrennte Schritte

Die Suche nach Zielordnern über ** oder Regex darf Unterverzeichnisse durchlaufen, auch wenn Recursive=false gesetzt ist. Recursive steuert erst danach die Bereinigung innerhalb jedes gefundenen Zielordners. Beispiel: **/Exports mit Recursive=false bereinigt die Dateien direkt in allen gefundenen Exports-Ordnern, aber nicht deren Unterordner. ExcludeDirectories wird sowohl bei der Zielsuche als auch bei der Bereinigung gegen den relativen Pfad zum ursprünglichen Selektor-Root geprüft; der Bezug wird nicht am gefundenen Exports-Ordner neu begonnen.

Glob/Regex prüfen ausschließlich Verzeichnisse. Die Altersregel und Dateimuster gelten weiterhin für jede Datei einzeln. Der Such-Root und alle als Ziel aufgelösten Ordner bleiben auch bei RemoveEmptyDirectories erhalten.

Auflösung, Überschneidungen und Fehler

Vor der ersten Löschung werden sämtliche Selektoren validiert und alle Zielordner vollständig aufgelöst. Ausgeschlossene Teilbäume und Reparse Points werden dabei nicht betreten. Gleiche oder überlappende Such-Roots sind innerhalb einer Regel nur bei identischem Root erlaubt; unterschiedliche überlappende Roots werden wegen verschiedener Ausschlussbezüge abgelehnt. Überlappende Suchbereiche verschiedener Regeln werden ebenfalls abgelehnt.

Bei identischem Root werden doppelte Treffer einer Regel zusammengeführt. Bei Recursive=true wird eine verschachtelte Zielmenge nur einmal durchlaufen; sämtliche ursprünglich ausgewählten Zielordner bleiben als geschützte Zielwurzeln erhalten. Bei Recursive=false bleiben verschachtelte Ziele eigenständig, weil jeweils nur ihre direkten Dateien bearbeitet werden. Die Selektorzuordnung wird für Logs beibehalten.

Die Auflösung ist auf 10.000 unterschiedliche Zielordner pro Lauf begrenzt. Ein Überschreiten führt zu Failed vor jeder Löschung; es wird keine willkürliche Teilmenge verwendet. Die Zielsuche bleibt abbrechbar. Null Treffer eines gültigen Musters ergeben DirectorySelectionEmpty auf Warning; ohne weitere Fehler kann der Lauf erfolgreich mit null Operationen enden. Ein nach Anwendung der Resilience-Regeln weiterhin fehlender oder unlesbarer Root, eine unvollständige Zielsuche oder ein Regex-Timeout beendet die Vorabphase ohne Löschung.

Regex-Syntax wird vorab geprüft. Jede Regex-Auswertung erhält ein festes Timeout von 100 ms; die .NET-Engine prüft dieses periodisch, es ist keine harte Echtzeitfrist. Ein Timeout ist ein Fehler, niemals ein Nichttreffer. Tritt er bei einem Ausschluss erst während der Bereinigung auf, endet der Lauf mit Fehler und Teilstatus; weitere Löschungen werden nicht gestartet. Zuvor ausgeführte Löschungen sind nicht rückgängig zu machen. Microsoft: Regex.MatchTimeout.

Die Zielmenge ist ein fester Stand pro Lauf; später neu entstehende Zielordner werden erst beim nächsten Lauf ausgewählt. Änderungen innerhalb eines ausgewählten Zielbaums können bei eingeschalteter Rekursion weiterhin sichtbar werden. Dry Run zeigt dieselbe Auflösung einschließlich Selektoren, Ausschlüssen und tatsächlichen Zielpfaden.

Zusammenführen mehrerer Provider

Für denselben Schlüssel gewinnt der zuletzt registrierte Provider. Das ist Verhalten der .NET-Konfiguration, keine Sonderregel dieses Pakets. Microsoft: Configuration Provider.

Listen werden nicht automatisch als Ganzes ersetzt. Ein späterer Provider kann etwa Rules:0:RetentionDays überschreiben, während andere Regelindizes aus einer früheren Quelle erhalten bleiben. Deshalb soll genau eine Quelle die Regellisten vollständig besitzen; andere Quellen überschreiben nur gezielt einzelne Werte. Das Binden darf nicht auf ein zuvor befülltes Optionsobjekt erfolgen.

Pro Lauf wird ein neues, tief kopiertes Optionsobjekt erstellt, vollständig validiert und unveränderlich verwendet. Ein Provider-Reload während des Bindens muss durch den Host verhindert oder durch einen atomaren Snapshot des Providers abgesichert werden. IConfiguration bietet allein keine atomare Momentaufnahme über alle Schlüssel. Änderungen gelten erst für den nächsten Lauf.

Unbekannte Schlüssel im Abschnitt, ungültige Werte, regelübergreifende Zielüberschneidungen, widersprüchliche Selektoren sowie ausgeschlossene Literalpfade außerhalb des Suchbereichs werden vor der ersten Löschung abgelehnt. Fehler nennen Regel und Konfigurationsschlüssel. Nicht erreichbare Ordner sind Laufzeitfehler, keine automatisch angelegten Ordner. Scheitert die Zielauflösung vorab, beginnt keine Löschung. Verschwindet ein bereits aufgelöstes Ziel später, wird dies im Lauf gesondert behandelt.

Berichts- und Seq-Einstellungen gehören zur Console. Das früh diskutierte ReportDirectory ist kein Core-Setting. Der Host kann das zurückgegebene Ergebnis als JSON speichern; lokale Logs und Puffer werden im vorhandenen Logging konfiguriert.

04 / FACHLICHES VERHALTEN

Wann wird etwas gelöscht?

Eine Datei ist nur dann Kandidat, wenn sie innerhalb eines erlaubten Zielbaums liegt, kein ausgeschlossener oder verknüpfter Pfad betroffen ist, mindestens ein Einschlussmuster passt, kein Ausschlussmuster passt und ihr Änderungsdatum strikt vor dem Stichtag liegt.

CutoffUtc = RunStartedUtc - RetentionDays × 24 Stunden
Eligible  = LastWriteTimeUtc < CutoffUtc
            UND Einschluss erfüllt
            UND kein Ausschluss
            UND Pfad zulässig

Alle Regeln verwenden dieselbe UTC-Startzeit, jedoch ihre eigene Frist. Ein Tag bedeutet hier exakt 24 Stunden: eine gleitende Aufbewahrungsfrist, keine Rundung auf lokale Mitternacht. Sommerzeit und Kalenderdatumswechsel verändern die Berechnung nicht. Zukünftige Zeitstempel gelten nicht als alt.

// RunStartedUtc ist ein DateTimeOffset mit Offset 00:00.
DateTimeOffset cutoffUtc = runStartedUtc.AddDays(-retentionDays);
bool isOldEnough = lastWriteTimeUtc < cutoffUtc;

Beispiel: 2026-09-14T02:00:00Z minus 90 Tage ergibt 2026-06-16T02:00:00Z. Genau auf dem Stichtag liegende Dateien bleiben erhalten. Eine Regel wie „alles vor dem lokalen Kalendertag vor 90 Tagen“ würde zusätzlich Zeitzone und Mitternachtsgrenze benötigen und ist nicht die hier definierte Altersregel.

Verzeichnisse

  • Recursive=false: ausschließlich Dateien direkt im Zielordner untersuchen.
  • Recursive=true: Unterverzeichnisse betreten und Ausschlüsse vor dem Betreten prüfen.
  • Leere Verzeichnisse von innen nach außen entfernen; ihr eigenes Alter ist unerheblich.
  • Bereits leere und erst durch die Bereinigung leer gewordene Verzeichnisse unterscheiden.
  • Der konfigurierte Zielordner wird niemals entfernt.
  • Nur nicht rekursiv löschen. Falls wieder Inhalt vorhanden ist, bleibt der Ordner bestehen.
  • Ausgeschlossene, nicht lesbare oder nur teilweise untersuchte Teilbäume gelten nicht als leer.

Grenzen und Sonderfälle

Symlinks, Junctions und andere Reparse Points werden weder verfolgt noch gelöscht. Konfigurierte Pfade und ihre Vorfahren werden ebenfalls geprüft. Laufwerks- und UNC-Freigabewurzeln sind ungültige Ziele. Die Pfadprüfung muss Verzeichnisgrenzen berücksichtigen: D:\Export2 ist kein Kind von D:\Export.

Schreibgeschützte Dateien werden mit Grund übersprungen; Attribute und Rechte werden nicht verändert. Normale versteckte Dateien werden nach denselben Regeln behandelt und müssen bei Bedarf explizit ausgeschlossen werden. Gesperrte Dateien können einen Löschfehler liefern; das Paket versucht keine erzwungene Freigabe.

Vor jeder Löschung werden Metadaten erneut gelesen und die Bedingungen erneut geprüft. Ist die Datei inzwischen zu jung, verschwunden oder als verändert erkennbar, wird sie übersprungen. Erneute Prüfung und Löschung sind über portable pfadbasierte APIs nicht atomar. Das Produkt garantiert daher weder Schutz gegen absichtlichen Pfadaustausch noch eine vollständige Dateisystemsnapshot-Sicht. Überlappende Zugriffe anderer Programme bleiben möglich.

05 / ERGEBNISSE

Dry Run und Statistik

Dry Run verwendet dieselbe Auswahlfunktion wie der produktive Lauf. Er schreibt keine Dateien im Zielbaum, ändert keine Zeitstempel absichtlich und entfernt nichts. Logs oder ein Ergebnisbericht außerhalb des Zielbaums sind erlaubt.

Die Verzeichnisvorschau berücksichtigt hypothetisch entfernte Kandidaten. Ein Ordner mit ausschließlich Kandidaten ist voraussichtlich leer; ein ausgeschlossener Eintrag, ein Link oder ein nicht untersuchter Bereich verhindert diese Aussage. Fehlende Löschrechte oder spätere Änderungen können das produktive Ergebnis abweichen lassen.

Löschlimit als konservative Grenze: Im echten Lauf wird nach der konfigurierten Zahl erfolgreicher oder ungeklärter logischer Datei-Löschoperationen sofort beendet. Verzeichnisnachbereitung wird dann nicht weiter ausgeführt. Der Status lautet Limited, auch wenn zufällig genau die letzte Datei erreicht wurde. Hardlinks, Komprimierung und gleichzeitige Änderungen verhindern eine belastbare Gleichsetzung von Dateigrößen mit tatsächlich freigegebenem Speicherplatz.

06 / MONITORING

Strukturierte Ereignisse für Seq

Das Paket verwendet ILogger<FileCleanUpService>, stabile EventIds und Nachrichtenvorlagen mit benannten Properties. Keine String-Interpolation für durchsuchbare Werte. Serilog und der Seq-Sink werden ausschließlich in der Kunden-Console konfiguriert. Seq: Microsoft.Extensions.Logging.

EventType, EventSchemaVersion, RunId, DryRun, PackageVersion und – bei regelbezogenen Ereignissen – RuleName. 07 / BETRIEBSGRENZEN

Was Logging garantiert – und was nicht

Ein erfolgreicher ILogger-Aufruf ist keine Empfangsbestätigung von Seq. Der Serilog-Sink überträgt standardmäßig asynchron und meldet Transportfehler nicht als reguläre Exception des Log-Aufrufers. Lokale persistente Pufferung verbessert die Zustellung, garantiert aber keine atomare Verbindung zwischen Dateilöschung und Protokoll. Datalust: Serilog und persistente Übertragung.

Vorgesehener Standardbetrieb

  • Persistente Seq-Pufferung in einem geschützten Verzeichnis außerhalb aller Zielbäume konfigurieren.
  • Logger beim regulären Beenden geordnet schließen und ausstehende Ereignisse übergeben.
  • Sink-interne Fehler, Pufferwachstum und freien Speicher überwachen; diese Fehler dürfen nicht ausschließlich an denselben gestörten Sink gemeldet werden.
  • Bei Seq-Ausfall weiterarbeiten, soweit die konfigurierte Pufferung funktioniert. Die Core-Bibliothek kann den Zustand des Sinks nicht verlässlich beurteilen.
  • Für kurzlebige Scheduler-Prozesse Nachlieferung über Folgeläufe oder einen separaten Versandprozess betrieblich sicherstellen und praktisch testen.

FileDeleted bedeutet: Der Löschaufruf kehrte ohne Fehler zurück. Manche Dateisystem-APIs tolerieren bereits fehlende Dateien. Ein konkurrierender Prozess kann die Datei zwischen Prüfung und Aufruf entfernen. Wir können daher nicht beweisen, dass ausschließlich dieser Prozess die Entfernung verursacht hat. Dokumentation und Statistik nennen diese Grenze ausdrücklich.

Vorübergehende Dateisystemausfälle überbrücken

Resilienz ist Bestandteil des ersten Releases. Ein kurzzeitiger Ausfall eines Laufwerks oder einer Netzfreigabe soll nicht sofort den Lauf scheitern lassen. Die Bibliothek wiederholt geeignete fehlgeschlagene Operationen begrenzt mit exponentiell wachsender Wartezeit und zufälliger Streuung (Jitter). Die Strategie gilt für Zielauflösung, Enumeration, Metadatenlesen und geeignete Löschfehler; auch lesende Operationen im Dry Run verwenden sie. Microsoft: Behandlung vorübergehender Fehler.

Die Budgets sind keine garantierten Betriebssystem-I/O-Timeouts. Ein blockierender synchroner Dateisystemaufruf kann länger dauern. Er wird nicht mittels Task.WhenAny „vergessen“, während parallel derselbe Löschaufruf erneut gestartet wird. Nach seiner Rückkehr werden Zeitbudget und Abbruch geprüft. Harte Prozessgrenzen sind Sache des Hosts und können ungeklärte Operationen hinterlassen.

Welche Fehler werden erneut versucht?

  • Temporär: ausdrücklich klassifizierte native Fehler wie Netzwerkunterbrechung, Netzwerkzeitüberschreitung oder ein vorübergehend nicht bereites Gerät. Kurzzeitige Sharing-/Lock-Verletzungen können ebenfalls wiederholt werden, sofern der Fehler garantiert, dass die Operation nicht ausgeführt wurde.
  • Dauerhaft: ungültiger Pfad, fehlende Berechtigung, ungültige Konfiguration, Regex-Fehler oder nicht unterstützte Pfadart. Keine Wiederholung. Keine pauschale Retry-Regel für jede IOException und keine Klassifikation anhand übersetzter Fehlermeldungen.
  • Unbekannt: keine automatische Wiederholung einer Mutation; Fehler mit Operation, Exception-Typ und nativem Fehlercode protokollieren. Der Windows-Adapter benötigt eine explizite, getestete Fehlercode-Zuordnung.
  • Nicht gefunden: ein fehlender Root wird begrenzt erneut geprüft, um ein kurzfristig verschwundenes Mount/Share zu überbrücken; danach ist er ein Fehler. Ein fehlender einzelner Eintrag gilt nur bei bestätigter Erreichbarkeit seines Elternbereichs als AlreadyMissing. File.Exists=false oder Directory.Exists=false allein belegen weder Nichtexistenz noch Erreichbarkeit.

Die verwendeten Leseoperationen müssen Fehler differenzierbar melden. File.Exists kann auch bei Fehlern false zurückgeben. Microsoft: File.Exists.

Verhalten beim Ausfall

  1. Beim transienten Fehler die aktuelle Operation pausieren. Keinen erfolgreichen Scan und keine Verzeichnisleere unterstellen.
  2. Vor einem erneuten Löschversuch Root, Pfadvorfahren, Reparse-Status, Metadaten und sämtliche Löschbedingungen neu prüfen. Stichtag und Konfiguration bleiben unverändert.
  3. Nach erfolgreicher Wiederherstellung fortsetzen und FileSystemRecoverySucceeded protokollieren. Vollständig behobene Fehler erhöhen RetryCount, aber nicht ErrorCount.
  4. Ist das Operationsbudget erschöpft, den betroffenen Bereich als unvollständig behandeln. Bei einer nicht verfügbaren Freigabe werden alle weiteren Ziele dieser Freigabe für den restlichen Lauf ausgelassen; bei lokalem Geräteausfall entsprechend das Volume. Keine neuen Retry-Schleifen für jede einzelne Datei. Ein isolierter Datei-Lock sperrt dagegen nicht die ganze Freigabe.
  5. Unabhängige erreichbare Speicherbereiche dürfen nach abgeschlossener Vorabphase weiterbearbeitet werden. Ist das globale Retry-Zeitbudget erschöpft, wird der gesamte Lauf mit Fehler und Teilstatus beendet. Eine unvollständige Zielauflösung stoppt weiterhin vor jeder Löschung.

Die Sperre für einen ausgefallenen Speicherbereich gilt nur für diesen Lauf; der nächste geplante Lauf versucht erneut. Kein zusätzlicher Hintergrunddienst und keine stillen Endlosschleifen. Zuordnung: UNC über Server/Freigabe, lokale Pfade über Volume. Aliase oder verschiedene Freigaben auf demselben Server können dieselbe physische Ablage bezeichnen; eine aliasübergreifende Erkennung wird nicht garantiert.

Enumeration ohne doppelte Verarbeitung wiederholen

Je Verzeichnis werden die direkten Einträge vor ihrer Verarbeitung vollständig als kurzlebige Liste gelesen. Bricht die Enumeration ab, wird diese unvollständige Liste verworfen und das Lesen des Verzeichnisses erneut begonnen. Erst nach vollständig erfolgreichem Lesen werden fachliche Zähler und Verarbeitung fortgesetzt. Metadatenprüfungen und Löschungen folgen danach; keine Neuverarbeitung eines bereits abgearbeiteten Verzeichnisses. Das benötigt Speicher proportional zur größten direkten Verzeichnisliste, nicht zum gesamten Dateibaum. Physische Enumerationsversuche werden getrennt von fachlichen Scan-Zählern erfasst.

Eine Wiederholung ist keine Dateisystemtransaktion. Nach erfolgreichem Einlesen neu erzeugte Einträge müssen nicht im Lauf enthalten sein. Verzeichnisleere wird unmittelbar vor der nicht rekursiven Löschung erneut geprüft; ein nicht vollständig bearbeitetes Verzeichnis und seine betroffenen Vorfahren bleiben erhalten.

Ungewisser Ausgang einer Löschung

Bei einer Netzwerkunterbrechung kann eine Löschung serverseitig bereits erfolgt sein, obwohl der Client einen Fehler erhält. Ein solcher Fehler ist kein sicherer Fehlschlag. Die Bibliothek protokolliert DeletionOutcomeUnknown und führt keinen blinden erneuten Löschaufruf am selben Pfad aus. Eine dort inzwischen neu angelegte Datei darf nicht als Wiederholung der alten Operation gelöscht werden.

Nach Wiederherstellung darf lesend abgeglichen werden: Ein jetzt fehlender Eintrag wird als MissingAfterUncertainDelete protokolliert, aber nicht als bestätigte eigene Löschung gezählt. Ein vorhandener oder nicht prüfbarer Eintrag bleibt für diesen Lauf ungeklärt. Der Lauf erhält mindestens CompletedWithErrors und IsPartial=true. Für garantierte „nicht ausgeführt“-Fehler sind Retries nach erneuter Prüfung erlaubt. Alle Versuche behalten dieselbe OperationId und erhalten eine eigene AttemptNumber.

Für MaxFilesToDeletePerRun zählen bestätigte erfolgreiche Dateilöschaufrufe plus ungeklärte Datei-Löschoperationen, da letztere bereits wirksam gewesen sein könnten. Mehrere Versuche derselben logisch unveränderten Operation verbrauchen keinen zusätzlichen Platz; ein späterer erfolgreicher Retry wird genau einmal gezählt. Bei ungewissem Ausgang wird der Platz nicht wieder freigegeben. So kann ein Übertragungsausfall das Löschlimit nicht umgehen.

Strenger Audit-Modus – Bestandteil von Version 1

Version 1 enthält einen aktivierbaren strengen Audit-Modus. Er ergänzt Seq um ein bestätigend geschriebenes lokales Journal. Seq bleibt die Monitoring-Oberfläche; das Journal dokumentiert Löschabsichten und Ergebnisse auch dann, wenn die Übertragung zu Seq ausfällt. Der neue Beispielstandard dieses Dokuments aktiviert Audit.Mode=Required.

Verbindliche Schreibreihenfolge

  1. Vor dem ersten Eingriff Journalverzeichnis exklusiv für den Lauf sperren, vorhandene Journale auf offene Vorgänge prüfen und einen RunStarted-Eintrag mit wirksamen Regeln, Fingerabdruck und Version bestätigen.
  2. Für jede Datei- und Verzeichnislöschung nach der letzten Auswahlprüfung einen DeleteIntent-Eintrag schreiben und dauerhaft flushen. Er enthält RunId, OperationId, AttemptNumber, Pfad, geprüfte Metadaten, Regel und Grund. Erst nach bestätigtem Schreiben darf der Löschaufruf beginnen.
  3. Nach dem Aufruf ein Ergebnis dauerhaft schreiben: Deleted, Failed, SkippedAfterRevalidation oder OutcomeUnknown. Notwendige Wiederholungen behalten die OperationId, erhalten aber eigene Versuchsnummern und jeweils einen bestätigten Intent vor dem mutierenden Aufruf.
  4. Nach erfolgreicher Intent-Persistierung nochmals geänderte Bedingungen verhindern die Löschung; auch dieses Auslassen bekommt ein Ergebnis. Der unvermeidbare kleine Zeitraum zwischen letzter Prüfung und Dateisystemoperation bleibt bestehen.
  5. Am Ende RunCompleted mit vollständigem Status und Statistik bestätigen. Erst danach darf die Bereinigung als vollständig erfolgreich gemeldet werden. Die Seq-Übertragung bleibt davon unabhängig asynchron.

Ein Mutationsergebnis darf erst nach bestätigtem Journalergebnis als reguläres FileDeleted/DirectoryDeleted-Ereignis an ILogger weitergereicht werden. Misslingt die Ergebnis-Persistierung nach einer Löschung, ist die Löschung möglicherweise bereits erfolgt. Die bestätigte Absicht bleibt offen; der Dienst stoppt, liefert Failed und IsPartial=true und erhöht den Zähler für ungeklärte Ergebnisse. Keine weitere Datei und kein weiteres Verzeichnis wird gelöscht.

Journalfehler und Wiederaufnahme

Fehlende Schreibrechte, voller Datenträger, beschädigte Journale, fehlgeschlagene Flushes oder eine belegte Journalsperre führen zu AuditUnavailable und Exitcode 1. Ein nicht bestätigter Intent erlaubt keine Löschung. Es gibt keinen automatischen Wechsel des Journalpfads und keine Fortsetzung nach einer Schreibstörung im selben Lauf. Die Resilience-Retries für Bereinigungsziele gelten nicht als blindes Wiederholen von Journal-Anhängen; ein mehrdeutiger Append-/Flush-Ausgang muss bei der Wiederherstellung geprüft werden.

Beim nächsten Start werden offene Intents, fehlende RunCompleted-Einträge und unvollständige Journalenden erkannt. Ein offener Intent beweist nur die Absicht, nicht die Ausführung. Pfade werden nicht automatisch erneut gelöscht. Ein lesender Abgleich hält Missing, Present oder Unavailable fest, kann aber den Verursacher einer Löschung oder die Identität einer neu angelegten Datei nicht zweifelsfrei bestimmen.

Required sperrt bei intakten, lesbaren Journalen nur die ungeklärten Pfade über Laufgrenzen hinweg. Andere Dateien dürfen im nächsten Lauf nach erneuter Prüfung bereinigt werden. Eine ungeklärte Verzeichnislöschung sperrt den gesamten zugehörigen Teilbaum; eine ungeklärte Dateilöschung sperrt exakt den normalisierten Pfad und verhindert die Entfernung seiner Vorfahren als leere Verzeichnisse. Gesperrte Pfade werden nicht als leer behandelt. Eine neue Datei am gleichen Pfad bleibt ebenfalls gesperrt, bis der Vorgang ausdrücklich geklärt ist. Der Lauf meldet CompletedWithErrors und IsPartial=true, solange solche Sperren einen ausgewählten Bereich betreffen. Ein beschädigtes, nicht lesbares oder nicht schreibbares Journal blockiert weiterhin sämtliche neuen Löschungen, weil die vollständige Sperrmenge nicht verlässlich bekannt ist. Dafür enthält der Paketvertrag eine explizite Recovery-API; die Beispiel-Console erhält einen bewussten Recovery-Aufruf. Er listet offene Vorgänge und erlaubt eine persistierte Bestätigung mit Operator-Kennung und Begründung. Diese Bestätigung ist keine nachträgliche Erfolgsmeldung. Reguläre Scheduler-Aufrufe nehmen keine solche Bestätigung vor. Ein fehlendes RunCompleted ohne offene Intents kann automatisch als unterbrochener Lauf abgeschlossen werden; eine beschädigte Integritätskette benötigt gesonderte Reparatur und wird nicht still übersprungen.

Format, Haltbarkeit und Berechtigungen

Vorgesehen sind versionierte, fortlaufende UTF-8-Journaldateien mit einzeln gerahmten Datensätzen: Sequenznummer, Länge, JSON-Nutzlast und Prüfsumme. Eine Hash-Verkettung erkennt unbeabsichtigte Änderungen innerhalb der vorhandenen Folge. Schreiben erfolgt exklusiv und sequenziell; die Bestätigung verlangt FileStream.Flush(flushToDisk: true). Ein reines FlushAsync ohne zugesicherte Datenträger-Persistierung reicht nicht als Vertragsnachweis. Die endgültige Implementierung muss Dateierstellung, Verzeichnis-Metadaten und Wiederherstellung nach Prozess-/Systemabbruch auf dem unterstützten Dateisystem prüfen.

Ein unvollständiger letzter Datensatz bleibt als Befund erhalten. Die Recovery-Funktion sichert den beschädigten Stand, stellt den letzten verifizierbaren Stand kontrolliert wieder her und protokolliert die Reparatur in einem neuen Segment. Unlesbare Bereiche werden nicht als „keine offenen Vorgänge“ behandelt. Rotation erfolgt nur an bestätigten Datensatzgrenzen; Segmentfolgen werden überprüfbar verknüpft.

Das ist kein atomarer Commit zusammen mit dem Dateisystem und keine Garantie gegen defekte Hardware oder absichtliche Manipulation durch Administratoren. Prüfsummen oder Hashes allein beweisen keine Revisionssicherheit; wer Journal und Prüfsummen ändern kann, kann sie neu erzeugen. Zugriff über Betriebssystemrechte auf den notwendigen Personenkreis begrenzen. Ein Hardware-/Stromausfall kann selbst bei angefordertem Flush von Speicherhardware und deren Zusagen abhängen.

Journaldateien werden in Version 1 nicht automatisch durch die Bibliothek gelöscht. Der Betreiber plant Speicherbedarf und externe Archivierung. Archivierung muss offene Vorgänge lokal auffindbar halten und vorhandene Segmentketten prüfen können; einfaches Entfernen einzelner Segmente ist unzulässig. Persistierung vor und nach jeder Löschung kostet zusätzliche I/O-Zeit; Required ist deshalb separat mit realistischen Dateimengen zu messen.

Dry Run, API und Seq

Auch ein Dry Run in Required prüft das Journal und schreibt Laufdaten sowie WouldDelete-Ereignisse außerhalb des Zielbaums. Er erzeugt keine mutierenden DeleteIntents und prüft keinen tatsächlichen Löschaufruf. Damit testet er Pfad, Rechte und grundsätzliche Persistierung, aber nicht alle Ausfallfenster eines echten Laufs.

Die Bibliothek enthält einen lokalen Journal-Writer hinter einem separaten ICleanupAuditJournal-Vertrag sowie einen ICleanupAuditRecoveryService für Inspektion, Abgleich und explizite Bestätigung. Diese Entwurfs-APIs sind Teil der geplanten Paketimplementierung. ILogger bleibt davon getrennt. Eine kundenspezifische Journalimplementierung muss denselben Bestätigungs- und Wiederherstellungsvertrag erfüllen; ein gewöhnlicher Seq-Sink kann nicht als bestätigender Journal-Writer eingesetzt werden.

Seq erhält zusätzlich AuditMode, JournalId, JournalSequence und AuditOutcome. Das Journal und Seq teilen RunId und OperationId. Eine Seq-Lücke löscht keine Journalinformation; eine automatische Nachlieferung aus dem Journal nach Seq ist in Version 1 nicht zugesagt. Dafür stehen Recovery-Inspektion und ein JSON-Export im API-Konzept bereit. Der Betreiber kann Ergebnisse so zuordnen, ohne eine zweite unkontrollierte Log-Pipeline einzuführen.

Öffentliche API und Host-Integration

Entwurfsvertrag: Die folgenden Typen und Methoden sind die geplante Oberfläche. NuGet-ID und Namespace lauten Minicon.FileCleanUp. Die tatsächliche Installation setzt ein veröffentlichtes Paket voraus.

public interface IFileCleanUpService
{
    Task<CleanupResult> RunAsync(
        CancellationToken cancellationToken = default);
}

// Vorgesehene Registrierungsüberladungen:
services.AddFileCleanUp(configurationSection);
services.AddFileCleanUp(cleanupOptions);

CleanupOptions enthält globale Optionen und CleanupRuleOptions. CleanupResult enthält Status, Flags, Zeitangaben, Summen und Ergebnisse je Regel. Es enthält keine unbegrenzt anwachsende Liste aller Dateien oder Exceptions. Einzelheiten fließen fortlaufend in die Ereignisse. Erwartete Datei- und Validierungsfehler liefern ein Ergebnis; falsche API-Argumente dürfen unmittelbar Exceptions auslösen.

Geplantes Console-Beispiel

using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using Minicon.FileCleanUp;

var builder = Host.CreateApplicationBuilder(new HostApplicationBuilderSettings
{
    Args = args,
    ContentRootPath = AppContext.BaseDirectory
});

// Eigenen Configuration Provider hier hinzufügen.
// Seine Werte haben Vorrang vor zuvor registrierten gleichen Schlüsseln.
// Vorhandenes Serilog-/Seq-Logging ebenfalls hier registrieren.

builder.Services.AddFileCleanUp(
    builder.Configuration.GetSection("FileCleanUp"));

using var host = builder.Build();
await host.StartAsync();

try
{
    var lifetime = host.Services.GetRequiredService<IHostApplicationLifetime>();
    var cleaner = host.Services.GetRequiredService<IFileCleanUpService>();
    var result = await cleaner.RunAsync(lifetime.ApplicationStopping);

    return result.Status switch
    {
        CleanupStatus.Succeeded => 0,
        CleanupStatus.InvalidConfiguration => 2,

}
finally
{
    await host.StopAsync();
}

Lifecycle und Abhängigkeiten

Der Service kann transient registriert werden; laufbezogene Statistiken und RunIds sind immer lokal zum Aufruf. Keine geteilte veränderliche Singleton-Statistik. Ein TimeProvider liefert testbare Zeit. Die Bibliothek hängt von Microsoft.Extensions-Abstraktionen für Logging, Konfiguration und DI ab, aber nicht direkt vom Seq-Sink oder einem kundenspezifischen Provider.

Bei explizit übergebenen Optionsobjekten wird zu Laufbeginn kopiert. Bei IConfiguration wird zu Laufbeginn neu gebunden. Es gibt keine Live-Änderung aktiver Regeln. Das Paket ersetzt keine bereits registrierten Host-Logger und erstellt keine globalen statischen Serilog-Instanzen.

Nach Validierung wird eine kanonische Darstellung der wirksamen Bereinigungsoptionen erzeugt und mit SHA-256 als ConfigFingerprint protokolliert. Eigenschaftsreihenfolge und Darstellung sind definiert; die relevante Regelreihenfolge bleibt erhalten. Keine vollständige Host-Konfiguration und keine Secrets aufnehmen. 11 / TECHNISCHES KONZEPT

Ausführung und Performance

  1. RunId und UTC-Startzeit erzeugen; CleanupStarted schreiben.
  2. Options-Snapshot erstellen, alle Regeln syntaktisch validieren und Zielpfade normalisieren.
  3. Stichtage berechnen, Fingerabdruck und wirksame Regeln protokollieren.
  4. Alle Verzeichnisselektoren vollständig auflösen, Überschneidungen prüfen, Ziele zusammenführen und geschützte Zielordner festhalten. Bei Auflösungsfehlern vor der Löschung beenden.
  5. Jeden Zielbaum mit expliziter, abbrechbarer Traversierung durchlaufen. Links und ausgeschlossene Teilbäume vor dem Betreten erkennen.
  6. Dateien mit einer gemeinsamen reinen Auswahlfunktion prüfen. Im Dry Run Kandidaten erfassen; sonst unmittelbar erneut prüfen.
  7. Bei Audit.Required bestätigten Intent schreiben, einzelne Löschoperation ausführen und Journalergebnis bestätigen. Bei Journalfehler keine weiteren Löschungen. Ergebnis oder Fehler an ILogger geben, Statistiken aktualisieren und Limit prüfen.
  8. Bei vollständiger Verarbeitung Verzeichnisse von innen nach außen auf tatsächliche oder hypothetische Leere prüfen.
  9. Regel- und Laufabschluss mit Status zurückgeben. Bei kooperativem Abbruch einen Teilbericht liefern.

Je Verzeichnis dessen direkte Einträge vollständig enumerieren, bevor sie verarbeitet werden; der gesamte Baum wird nicht vorab eingelesen. Microsoft: Directory.EnumerateFiles. Keine vollständige baumweite Dateiliste und keine Sortierung aller Dateikandidaten im Speicher. Für sichere Wiederholung abgebrochener Enumeration wird jeweils eine direkte Verzeichnisliste gepuffert. Die vorab aufgelöste, auf 10.000 Einträge begrenzte Zielordnermenge wird dagegen im Speicher gehalten. Eine explizite Stack-Traversierung vermeidet einen tiefen rekursiven Aufrufstapel; Ressourcen und Enumeratoren werden zuverlässig freigegeben.

Die erste Version arbeitet sequenziell. Dateisystemzugriffe sind nicht allein durch eine Task-Signatur asynchron. Cancellation wird zwischen Einträgen und bei Wartezeiten geprüft; blockierende Dateisystemaufrufe können nicht immer sofort unterbrochen werden. Parallelisierung erfolgt erst nach Messungen und gesonderten Semantiktests.

Die Größenordnung mehrerer Tausend Dateien rechtfertigt keine pauschale Verzögerung. Standard ist 0 ms. Für Netzfreigaben zählen Serverlatenz, Virenscanner, Dateisystemrechte und Protokollvolumen. Der begrenzte Resilience-Mechanismus ist Bestandteil der ersten Version; seine Fristen und Ereignisse sind im Kapitel Audit & Zuverlässigkeit festgelegt.

Interne Module

Validator, Verzeichnisselektor, Auswahlfunktion und Ausführungsdienst bilden den Kern; eine Resilience-Komponente und das bestätigende Audit-Journal mit Recovery ergänzen ihn. Eine schmale interne Dateisystemgrenze erleichtert gezielte Fehlertests. Keine Factory-, Provider- oder Decorator-Kette ohne belegten Nutzen. Der kundeneigene Configuration Provider bleibt Bestandteil des Hosts.
